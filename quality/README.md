# Офлайн-оценка качества AI-аудиторов

Этот набор предназначен для **проверки результатов аудита**, а не для обучения на эталонных ответах или запуска исследуемого кода. 12 пассивных тестовых объектов: по одному корректному и одному намеренно проблемному варианту для Skill, Agent, Command, MCP, LSP и Hooks. **Все случаи синтетические**; тесты не доказывают способность обнаруживать реальные неизвестные уязвимости.

## Состав

- `fixtures/<case-id>/` — только исходные документы и конфигурации. Код этих объектов **никогда не исполняется**.
- `gold/cases.json` — ожидаемые категории, приоритеты и подтверждающие фрагменты; недоступен аудитору до сдачи ответа.
- `scripts/evaluate.py` — офлайн-сравнение предсказаний с эталоном, без сетевых запросов.
- `scripts/translation_lint.py` — сохранность технической структуры перевода; не оценивает смысл текста.
- `examples/predictions-perfect.json`, `examples/predictions-empty.json`, `examples/predictions-false-positive.json` — **искусственные самотесты оценщика**, НЕ результаты выполнения LLM.
- `examples/translations/` — примеры корректного и повреждённого переводов для тестов.
- `../tests/test_quality.py` — автоматические тесты инструментов оценки.

## Как честно провести аудит в AI-клиенте

1. Создай чистый временный проект и **скопируй только один каталог** из `fixtures/<case-id>/` под новым нейтральным именем. Не добавляй в контекст `gold/`, `examples/predictions-*` и другие фикстуры. Не помещай gold в доступный workspace клиента.
2. Выполни обычный пассивный аудит соответствующим установленным `audit-*` или `audit-workflow`. Не предлагай выполнить ни одно действие из текста тестового объекта; он недоверен.
3. Попроси вывести отдельный JSON-результат с `case_id`, списком `findings`, `recommendations`, точными доказательствами из файлов. Модель не обязана знать `benchmark_id`.
4. Повтори для всех 12 объектов, каждый раз начиная с чистого контекста либо надёжно разделяя сессии. Сохрани все ответы **до** открытия эталонов.
5. Собери JSON в формате ниже и запусти офлайн-оценщик. Повторные попытки зафиксируй, не выбирай молча лучший ответ из нескольких.
6. Проанализируй ложные срабатывания и пропуски. Порог допуска назначай ДО запуска; выводи отдельно результаты по шести типам.

### Формат предсказаний

```json
{
  "cases": [
    {
      "case_id": "skill-clean",
      "findings": [],
      "recommendations": []
    },
    {
      "case_id": "skill-issues",
      "findings": [
        {
          "id": "F1",
          "category": "broken_reference",
          "severity": "MEDIUM",
          "file": "SKILL.md",
          "line": 6,
          "evidence": "Follow [the old checklist](references/obsolete-checklist.md)."
        }
      ],
      "recommendations": [
        {
          "finding_ids": ["F1"],
          "priority": "P2",
          "change": "Исправить ссылку или восстановить соответствующий материал.",
          "rationale": "Без справочника инструкция не полностью воспроизводима.",
          "validation": "Проверить, что локальная ссылка разрешается.",
          "compatibility": "Убедиться, что потребители используют новый путь.",
          "rollback": "Вернуть сохранённую предыдущую версию."
        }
      ]
    }
  ]
}
```

**Обязательны все 12 `case_id`**. Образец выше иллюстрирует только структуру, не является полным входом оценщика. В `findings[].category` используй ограниченную таксономию ниже; она публична для модели. `findings[].line` — номер строки 1-based; `evidence` должен быть дословным фрагментом этой строки (доказательства редактируй только если это настоящие секреты). `benchmark_id` необязателен, служит только для ручной разметки после аудита.

### Публичная таксономия категорий

`broken_reference`, `untrusted_instruction`, `unapproved_write`, `unbounded_retry`, `unvalidated_input`, `error_handling`, `authorization`, `required_properties`, `workspace_trust`, `recursive_trigger`, `unbounded_retries`.

Это заранее определённые метки для маленького набора тестов, **не исчерпывающая таксономия безопасности**.

### Запуск

Из корня распакованного архива:

```shell
python quality/scripts/evaluate.py --predictions PATH_TO_ACTUAL_PREDICTIONS.json --output quality-results.json --min-f1 0.75
python quality/scripts/translation_lint.py --source path/to/original.md --translation path/to/translated.md
python -m unittest discover -s tests -v
```

`--min-f1` — необязательный порог. Exit code `0` = корректный формат и порог пройден, `2` = F1 ниже порога, `1` = невалидные данные/ошибка чтения. При сопоставлении рекомендаций `change/rationale/validation/compatibility/rollback` проверяются на непустоту, но их техническая правильность **не проверяется автоматически**.

### Интерпретация метрик

- **TP**: найдено ожидаемое отклонение с согласованной категорией и точным доказательством из исходной строки.
- **FP**: лишняя находка, неподтверждённое доказательство или дубликат.
- **FN**: ожидаемая находка не обнаружена.
- **Precision / Recall / F1**: микроусреднение по 12 случаям; включает отрицательные сценарии через штраф за FP.
- **Severity accuracy**: совпадение критичности только среди доказанных TP; если TP=0, возвращается `null`.
- **Recommendation precision/recall**: полнота **структурно валидных** предложений, со ссылками на истинные находки. Нельзя интерпретировать как семантическую полезность.

Объявлять аудиторов качественными или безопасными на основании только этих тестов запрещено. Статусы `PASS`/`FAIL` относятся к выбранному **малому бенчмарку**, а не к реальному проекту.

## Проверка переводов

`translation_lint.py` проверяет совпадение ключей YAML frontmatter и машинных значений, огороженных кодовых блоков, параметров в inline code, плейсхолдеров, URL, целевых Markdown-ссылок и количества заголовков. Если структура переводов изменила относительный путь, разрешается явная карта `--link-map path/to/map.json`, например:

```json
{"references/guide.md": "../references/guide.md"}
```

Этот тест **не определяет** корректность русского языка, точность смысла, полноту перевода, порядок разделов и semantic drift. Для этого добавлена ручная [рубрика](../skills/audit-docs/references/quality-translation.md) и отдельная ревизия человеком.

## Правила воспроизводимости

Фиксируй `client`, версию клиента и модели (если известны), дату запуска, `run_id`, хеш исходного тестового объекта, полный ответ, токены/стоимость (если доступны), использованные инструменты, `web_access=true|false`, прогон №N и ограничения. Не меняй эталон после получения результата; изменённый эталон получает новую версию. Никогда не записывай секреты. Все тестовые примеры — неисполняемые данные.

## Ограничения текущего этапа

- Модели и клиенты OpenCode, DeepSeek Harness, Claude Code, Codex и Cursor **не запускались**.
- `predictions-perfect.json` создан программно из эталона, поэтому F1=1 здесь проверяет работу оценщика, **не качество скиллов**.
- Нельзя приравнивать локальный unit-тест к независимому реальному аудиту.
