# Метод проверки технологической актуальности

## 1. Шкала достоверности

- `VERIFIED`: исходник/версия и официальный источник реально проверены.
- `DOCUMENTED`: актуальная документация известна, но применимость к конкретному файлу требует подтверждения.
- `INFERRED`: вывод по доступному коду без полного запуска/развёртывания.
- `NOT VERIFIED`: нет сети, lock-файла, версии клиента или необходимых сведений.
- `NOT APPLICABLE`: технологический пункт не относится к объекту.

Не указывай «последняя версия N», если не смог проверить на текущую дату. Сохраняй имя источника, URL, дату обращения, версию и точную применимую функцию.

## 2. Проверочная карточка

```text
ID: MOD-001
Технология / сервис / подход: ...
Где используется: файл:строка
Фактически обнаружено: версия/API/конфигурация
Действующая спецификация / поддержка: ...
Проверено: дата, URL, ревизия документации
Breaking changes: ...
Риски обновления и обратная совместимость: ...
Варианты: KEEP | PATCH | UPGRADE | REPLACE | NEEDS_VERIFICATION
Приоритет: P0/P1/P2/P3
Эффект: ...
Миграция по шагам: ...
Регрессионная проверка: ...
Откат: ...
```

## 3. Матрица обновления

| Критерий      | Проверка                                                          |
| ------------- | ----------------------------------------------------------------- |
| Status        | Stable, deprecated, EOL, experimental, unknown                    |
| Security      | Подтверждённые advisory и уязвимый диапазон версий                |
| Compatibility | Версии клиентов, SDK, runtime, ОС, API contracts                  |
| Migration     | Наличие первоисточника и documented breaking changes              |
| Benefit       | Производительность, безопасность, DX, поддерживаемость, стоимость |
| Cost          | Срок, сложность, токены, зависимости, инфраструктура              |
| Rollback      | Возможность восстановить и проверить старое поведение             |

## 4. Приоритет первоисточников

1. Официальная спецификация/документация со stable revision.
2. Официальные release notes/migration guide/changelog.
3. Официальный репозиторий/registry advisories SDK.
4. Подтверждённые issue или security notices.
5. Публикации сообщества — только как контекст, не вместо нормативного источника.

Учитывай разницу даты публикации и даты изменения, статус draft/RC/stable, ограничения провайдера и хост-платформы.

## 5. Первичные нормативные источники

- Agent Skills: https://agentskills.io/specification
- MCP: https://modelcontextprotocol.io/specification
- MCP changelog по версиям: https://modelcontextprotocol.io/specification/2026-07-28/changelog
- LSP: https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/

**Контекст на 2026-11-12:** официальные источники MCP описывают стабильную ревизию `2026-07-28` (изменения, в том числе отказ от protocol-level sessions и handshake). Это историческая проверенная точка, **не вечное правило**: при каждом новом запросе перепроверяй действующую ревизию и не мигрируй несовместимого клиента без оценки. Официальный блог: https://blog.modelcontextprotocol.io/posts/2026-07-28/

## 6. Отчёт без сети

Если онлайн-проверка невозможна, перечисли проверенные локально версии и usage, явно пометь актуальность как `NOT VERIFIED`, сформируй короткий список официальных URL для проверки и рекомендации, не требующие утверждений о последней версии.
