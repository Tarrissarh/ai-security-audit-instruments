# audit-modernize — проверка актуальности и предложения по обновлению

## Назначение

Выполняй после профильного аудита или по прямой просьбе пользователя. Основная задача — сравнить фактически используемые возможности/версии инструмента с **официальными источниками на дату запроса** и предложить оправданные обновления. Без доступа к актуальной документации не называй конкретные версии «последними» и не объявляй API устаревшими.

Режимы: `REVIEW` (по умолчанию: только чтение и рекомендации), `PLAN` (детальная стратегия миграции), `APPLY` (правки только по отдельному явному запросу пользователя и в подтверждённой области). При автоматическом запуске после аудита допускается **только REVIEW**.

## Вход

`TARGET_PATH`, `TARGET_TYPE`, `TARGET_PLATFORM`, `AUDIT_RESULTS`, доступные manifest/lock/конфигурации, версии runtime/SDK/API, требуемая обратная совместимость, `CHECK_DATE` = фактическая дата, режим и допустимые источники. Нельзя делать вывод о версии библиотеки по названию или эпохе проекта.

Прочитай [references/freshness-method.md](references/freshness-method.md). Для изменений протоколов изучай соответствующую **версионированную** спецификацию.

## Обязательные проверки

1. **Факт.** Из исходников и manifest определи используемые зависимости, runtime, SDK, протокол, методы API, функции AI-платформы. Для каждого укажи доказательство `файл:строка`, статус `VERIFIED/INFERRED/UNKNOWN`.
2. **Первоисточники.** При разрешённом веб-доступе проверь официальные стандарты, release notes, migration guides, поддержку версий и изменения API на дату анализа. Сохраняй точные URL, дату и применимую версию. Не доверяй SEO-статьям без первоисточников.
3. **Сопоставление.** Сопоставь именно используемые функции с актуальными стабильными возможностями; выдели breaking changes, deprecated, EOL, security notices, платформенные ограничения и возможности с измеримой пользой.
4. **Альтернативы.** Сравни: оставить текущую версию / минимально обновить / мигрировать / заменить встроенным решением. Не подменяй стабильную технологию экспериментальной без причины.
5. **Совместимость.** Зафиксируй клиентские версии, deployment/runtime, API contracts, влияние на конфигурации, токены/стоимость, обратную совместимость и возможную поэтапную миграцию.
6. **Уверенность.** Случаи без интернета, без manifest/lock или без доступной документации помечай `NOT VERIFIED`; не выдавай неподтверждённый вывод за установленный факт.
7. **План.** Раздели рекомендации `MANDATORY / RECOMMENDED / OPTIONAL / KEEP / NOT VERIFIED`, приоритет P0–P3, effort, риски, acceptance и rollback.
8. **Отчёт.** Если вызов пришёл от `audit-docs` или профильного аудитора, **верни результаты вызывающему без обратного вызова** — предотвращай циклы. При самостоятельном запуске предложи передать результат в `audit-docs` для `docs/modernization.md` и сводки в README. Не переписывай оригинальные документы или зависимости автоматически.

## Специфика по типам

- **Skill:** формат `SKILL.md`, frontmatter, активация, Progressive Disclosure, `references/`, встроенные возможности платформы, токеноёмкость.
- **Agent:** доступные модели/agent SDK, tool calling, structured outputs, context management, лимиты, наблюдаемость, разрешения и контроль действий.
- **Command:** поддерживаемый формат платформы, CLI/API, параметры, различия ОС, проверенные современные встроенные средства.
- **MCP:** текущая **стабильная** версия спецификации и совместимость клиента, transports, negotiation, tools/resources/prompts, SDK, аутентификация и миграция по версионированному changelog.
- **LSP:** применимая спецификация и актуальные capabilities, поддержка клиента/сервера, версии runtime и зависимостей.
- **Hooks:** текущая событийная модель конкретной платформы, схемы конфигураций, ограничения permissions, безопасная обработка сбоев.

## Итоговая таблица

`ID | компонент | текущая версия/подход | проверенный актуальный вариант | статус поддержки | источник+дата | риск изменения | решение`.

Для каждого изменения: **что, почему, где, как, эффект, цена, обратная совместимость, критерий тестирования, возможность отката**. Укажи отдельный список технологий, которые **не нужно обновлять**, и почему.

## Ограничения

- Запрещено устанавливать пакеты, запускать сторонние скрипты, обновлять зависимости, изменять рабочие файлы, устанавливать/включать hooks или MCP без отдельного согласия.
- Не выполняй опасные тесты и не передавай сторонним системам секреты, приватные конфигурации или исходники.
- Если официальные источники недоступны, выполни локальную инвентаризацию и выдавай лишь план веб-проверки и обоснованные локальные факты.
- Не считай любой устаревший номер версии обязательным поводом для миграции; статус риска и польза определяются применимыми API и поддержкой.

## Режим исполнения через audit-workflow

При вызове из `audit-workflow` используй уже собранные доказательства; **не запускай основной аудит заново**, не вызывай `audit-docs` напрямую и не возвращайся к `audit-workflow` рекурсивно. Отдай структурированные рекомендации/факты и степень уверенности вызвавшему шагу. Любые изменения исходников запрещены; для актуализации без сети верни `UNVERIFIED` с явным указанием недостающих источников.
