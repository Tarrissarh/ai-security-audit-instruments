# Полный шаблон отчёта (из исходного audit-docs)

Файл(ы) отчёта должны быть на русском языке. Приведённые ниже 14 тем **обязательны для всего набора отчётных документов в целом**, а не обязательно для одного `README.md`. Краткие выводы — в README, полные материалы — в `docs/**/*.md` согласно [output-structure.md](output-structure.md).

Используй следующую структуру, распределяя подробности по тематическим файлам:

# Отчёт об аудите [Название инструмента]

### 1. Общая информация

Укажи:

- Название инструмента.
- Тип инструмента.
- Разработчика.
- Источник получения.
- Версию или commit, если известны.
- Дату проведения аудита.
- Назначение.
- Поддерживаемые платформы.
- Требуемые разрешения.
- Основные зависимости.
- Общий уровень риска.
- Итоговый вердикт.

### 2. Краткое описание

Объясни простым языком:

- Для чего нужен инструмент.
- Какие задачи решает.
- Как работает.
- Какие возможности предоставляет.
- Чем полезен пользователю.
- Какие ограничения имеет.
- Когда его целесообразно применять.

### 3. Установка и использование

Опиши:

- Требования к окружению.
- Порядок безопасной установки.
- Подключение к AI-клиенту или IDE.
- Необходимые параметры конфигурации.
- Примеры штатного использования.
- Минимально необходимые разрешения.
- Ограничения безопасности.

Примеры являются документацией, а не командами для выполнения аудитором.

### 4. Архитектура и структура

Перечисли основные файлы и каталоги.

Объясни назначение компонентов.

Покажи основные потоки данных:

`Входные данные → Обработка → Внешние вызовы → Результат`

Отдельно отметь границы доверия, участки с доступом к секретам и компоненты, способные изменять состояние системы.

### 5. Результаты функциональной проверки

Используй таблицу:

| ID  | Компонент | Проверка | Результат | Проблема | Приоритет |
| --- | --------- | -------- | --------- | -------- | --------- |

Оцени:

- Соответствие документации реализации.
- Ошибки логики.
- Качество архитектуры.
- Обработку ошибок.
- Производительность.
- Совместимость.
- Избыточные зависимости.
- Неиспользуемые компоненты.
- Потенциальные конфликты.
- Корректность интеграции с AI-клиентом.

Каждую существенную проблему опиши подробно.

### 6. Полный отчёт по безопасности

Укажи количество обнаруженных проблем:

| Уровень  | Количество |
| -------- | ---------- |
| CRITICAL | ...        |
| HIGH     | ...        |
| MEDIUM   | ...        |
| LOW      | ...        |
| INFO     | ...        |

Критерии отнесения к уровню (для единообразия во всех отчётах):

| Уровень  | Критерий                                                                                                                   |
| -------- | -------------------------------------------------------------------------------------------------------------------------- |
| CRITICAL | Немедленное неконтролируемое действие: исполнение произвольного кода, утечка секретов, изменение доступа без подтверждения |
| HIGH     | Реальная уязвимость с серьёзными последствиями или опасный автоматический сценарий без штатных ограничений                 |
| MEDIUM   | Потенциальный риск при определённых условиях либо избыточные полномочия без немедленного эксплойта                         |
| LOW      | Незначительное нарушение гигиены, переносимости или корректности с ограниченным влиянием                                   |
| INFO     | Наблюдение или рекомендация без прямого риска; сведения для улучшения                                                      |

Для каждой находки укажи:

- Уникальный идентификатор.
- Название.
- Категорию.
- Критичность.
- Статус подтверждения.
- Уверенность аудитора.
- Путь к файлу.
- Номера строк, если доступны.
- Фрагмент кода или конфигурации с маскировкой секретов.
- Техническое объяснение.
- Условия возникновения.
- Потенциальные последствия.
- Способ устранения.
- Способ проверки исправления.

Проверь применимые категории:

- Prompt Injection.
- Tool Poisoning.
- Command Injection.
- Path Traversal.
- Небезопасное выполнение кода.
- Утечки конфиденциальных данных.
- Несанкционированный сетевой доступ.
- Избыточные разрешения.
- Опасные операции с файлами.
- Небезопасное использование сторонних API.
- Уязвимые зависимости.
- Supply Chain Security.
- Неконтролируемые действия AI-агента.
- Опасные автоматические операции.
- Прочие риски, характерные для типа инструмента.

Не выдавай непроверенные подозрения за подтверждённые уязвимости.

### 7. Анализ зависимостей

Предоставь таблицу:

| Зависимость | Версия | Назначение | Проблема | Рекомендация |
| ----------- | ------ | ---------- | -------- | ------------ |

Отдельно оцени:

- Неиспользуемые зависимости.
- Устаревшие библиотеки.
- Необоснованные пакеты.
- Неизвестные источники загрузки.
- Незафиксированные версии.
- Опасные установочные скрипты.
- Известные уязвимости, если они действительно проверены по актуальным источникам.

Если актуальная проверка CVE/GHSA/OSV невозможна, явно напиши об этом.

### 8. Что нужно улучшить

Это обязательный раздел.

Проанализируй инструмент с точки зрения:

1. Безопасности.
2. Архитектуры.
3. Функциональности.
4. Производительности.
5. Совместимости.
6. Удобства использования.
7. Качества инструкций.
8. Поддерживаемости и расширяемости.

Предоставь таблицу:

| ID  | Что улучшить | Почему | Как улучшить | Приоритет |
| --- | ------------ | ------ | ------------ | --------- |

Для каждого улучшения объясни:

- Какую проблему решает изменение.
- Что конкретно нужно изменить.
- В каких файлах.
- Как это реализовать.
- Какие будут преимущества.
- Есть ли риски от изменения.
- Как проверить результат.

Не ограничивайся общими фразами вроде «улучшить безопасность» или «оптимизировать код».

Предлагай конкретные технические действия, основанные на изученных материалах.

### 9. Что лучше убрать

Это обязательный раздел.

Проверь наличие:

- Лишних инструкций.
- Дублирующихся правил.
- Неиспользуемых функций.
- Ненужных файлов.
- Устаревших механизмов.
- Избыточных разрешений.
- Опасных автоматических действий.
- Необоснованных зависимостей.
- Избыточных сетевых запросов.
- Лишних обращений к LLM.
- Неиспользуемых конфигураций.
- Противоречивых инструкций.
- Чрезмерно сложных компонентов.

Предоставь таблицу:

| Объект | Файл | Почему убрать | Чем заменить | Последствия |
| ------ | ---- | ------------- | ------------ | ----------- |

Для каждого пункта:

1. Укажи конкретное расположение.
2. Объясни причину удаления.
3. Определи, используется ли компонент другими частями инструмента.
4. Оцени последствия удаления.
5. Предложи замену, если она необходима.
6. Объясни, как проверить отсутствие регрессий.

Не рекомендуй удалять компонент только потому, что его назначение непонятно.

Если отсутствуют доказательства ненужности, пометь рекомендацию как требующую дополнительной проверки.

**Аудитор не должен автоматически удалять указанные компоненты.**

### 10. Что следует добавить

Предложи дополнительные возможности, которые могут повысить качество инструмента.

Рассматривай только дополнения, соответствующие его назначению.

Примеры:

- Валидация входных данных.
- Ограничение разрешений.
- Безопасная обработка ошибок.
- Подтверждение опасных операций.
- Логирование без чувствительных данных.
- Конфигурируемые ограничения.
- Обработка таймаутов.
- Документация.
- Тестирование.
- Поддержка безопасного отключения функций.

Для каждого дополнения объясни пользу, сложность и приоритет.

Не предлагай увеличение сложности без обоснованной необходимости.

### 11. План исправлений

Составь дорожную карту:

#### P0 — критически важно

Изменения, необходимые для устранения критических рисков.

#### P1 — высокий приоритет

Исправления существенных уязвимостей и серьёзных функциональных ошибок.

#### P2 — средний приоритет

Улучшение качества архитектуры, поддерживаемости и стабильности.

#### P3 — низкий приоритет

Необязательные оптимизации и косметические улучшения.

Для каждого действия укажи:

- Приоритет.
- Затрагиваемые файлы.
- Рекомендуемое изменение.
- Ожидаемый результат.
- Способ проверки.

### 12. Рекомендованная безопасная конфигурация

Опиши, как использовать инструмент с минимальными рисками.

Укажи:

- Какие разрешения оставить.
- Какие отключить.
- Какие операции требуют подтверждения.
- Какие ограничения установить.
- Как обеспечить изоляцию.
- Как контролировать передачу данных.
- Как безопасно обновлять инструмент.
- Как отключить или удалить инструмент.

### 13. Полнота и ограничения аудита

Укажи:

- Какие файлы изучены.
- Какие файлы не удалось проверить.
- Какие проверки выполнены.
- Какие проверки не выполнены.
- Был ли доступ к актуальным источникам уязвимостей.
- Проводился ли динамический анализ.
- Какие выводы нельзя подтвердить без выполнения инструмента.
- Какие риски остаются неизвестными.

Дополнительно приведи **матрицу покрытия** — для каждой профильной проверки укажи её
фактический статус и итог:

| Профильная проверка | Статус | Комментарий |
| ------------------- | ------ | ----------- |
| …                   | VERIFIED / UNVERIFIED / NOT TESTED / NOT APPLICABLE | … |

Итог: «Покрытие: N из M профильных проверок выполнено». Статус `NOT TESTED` означает,
что проверка не проводилась (например, динамический анализ), `UNVERIFIED` — результат
не подтверждён источниками, `NOT APPLICABLE` — проверка неприменима к объекту. Эта же
матрица отражается в `coverage` документа `findings.json`.

### 14. Итоговый вердикт

Используй один из вариантов:

- МОЖНО ИСПОЛЬЗОВАТЬ.
- МОЖНО С ОГРАНИЧЕНИЯМИ.
- НЕ РЕКОМЕНДУЕТСЯ.
- НЕЛЬЗЯ РЕКОМЕНДОВАТЬ К ИСПОЛЬЗОВАНИЮ.
- НЕДОСТАТОЧНО ДАННЫХ.

Дополнительно укажи:

- Общий уровень риска.
- Основные проблемы.
- Обязательные действия перед использованием.
- Наиболее полезные улучшения.
- Компоненты, которые стоит убрать.
- Остаточные риски.

## Требования к качеству всех отчётных документов

- Используй русский язык.
- Не сокращай описание существенных проблем.
- Не придумывай результаты проверок.
- Ссылайcя на конкретные файлы и строки.
- Отделяй подтверждённые факты от предположений.
- Не включай реальные пароли или токены.
- Не удаляй обязательные темы при отсутствии результатов: укажи «Не обнаружено» или «Не проверено» с объяснением.
- Не объявляй инструмент полностью безопасным.
- Сохраняй единый формат отчёта для всех типов инструментов.
- Не изменяй сам инструмент для устранения найденных проблем.

## Дополнительная проверка технологической актуальности

Когда профильный аудитор собрал подтверждённые сведения о версиях/SDK/API/протоколах, отражай в `docs/compatibility.md` или `docs/modernization.md`:

- Используемое решение и заявленную/обнаруженную версию (не угадывай).
- Фактически проверенную актуальную версию/статус поддержки, дату и ссылку на первоисточник, если проверка выполнялась.
- Deprecated/breaking changes, относящиеся к целевой среде.
- Альтернативы с аргументами по безопасности, сложности и обратной совместимости.
- Решение: обязательно обновить / желательно / можно оставить / не удалось проверить.

Без доступа к актуальной документации не утверждай точные последние версии или наличие CVE. Новизна сама по себе не основание переписывать работающий инструмент.

## Дополнительные разделы для расширенного комплекса аудита

### 15. Недостающие AI-инструменты и зависимости

Если проверялся набор связанных инструментов, включи перечень ссылок `имя | тип | источник (файл:строка) | обязательность | FOUND/MISSING_CONFIRMED/NOT_DISCOVERABLE/UNVERIFIED/BUILT_IN/OPTIONAL/UNSUPPORTED | доказательство | альтернатива`. Подробности при необходимости вынеси в `docs/missing-tools.md`. Если отсутствующий инструмент действительно нужен, предложи человеку **ручной** запуск `ai-tool-generator`, но не вызывай его автоматически.

### 16. Предложения audit-improve

Если доступен завершённый результат `audit-improve`, в `docs/improvements.md` размести конкретный список `ID | P0-P3 | источник | изменение | эффект | сложность | риск | проверка | откат`. Сохрани аргументацию «до/после», решения `KEEP` и неподтверждённые гипотезы. Не превращай предложение в сообщение о выполненном исправлении. Если скилл недоступен, честно укажи, выполнялся ли такой анализ.

### 17. Проверка актуальности audit-modernize

Если результат `audit-modernize` подтверждён, сформируй `docs/modernization.md` с версионированными источниками, датой проверки, status/support, breaking changes, приоритетами и планом миграции, в том числе рекомендациями **оставить** работающие решения. Если онлайн-источники были недоступны, не выдавай «актуальную» версию без подтверждения.
