# Модульная документация и переводы — обязательные правила

> Применяется скиллом `audit-docs` после профильных проверок `audit-skill`, `audit-agent`, `audit-command`, `audit-mcp`, `audit-lsp`, `audit-hooks` при **создании результатов анализа стороннего инструмента**. Это руководство относится к выходным артефактам, а не к редактированию исходного объекта. Его необходимо читать целиком до записи отчётов.

## 1. Расположение и границы записи

- `AUDIT_OUTPUT_DIR` — целевой каталог результатов. По умолчанию используй каталог именно проверяемого стороннего инструмента, **если** он однозначно определён, доступен для записи и место для отчёта согласуется с существующей структурой. Не записывай результат в каталог текущего аудитора.
- Если исходный `README.md` — важная документация проекта, **не уничтожай его**: по умолчанию используй `<целевой каталог>/audit/` для новых `README.md`, `docs/` и `translations/`; если пользователь явно указал другое расположение, соблюдай его при возможности безопасной записи. Для замены существующего отчёта, созданного прошлым запуском, сначала сохрани резервную копию.
- Если инструмент передан архивом, URL, одиночным файлом либо путь неоднозначен, используй отдельную папку для результатов, например `audit/<tool-type>/<tool-name>/`, и не меняй оригинал.
- Директории `docs/` и `translations/` находятся **рядом с выходным README.md**. Запрещено без разрешения менять исходные файлы, исходные инструкции, скрипты, конфигурации, зависимости, разрешения, Git-историю.
- Создавай только реально необходимые файлы и подкаталоги; никаких пустых файлов ради шаблона.

## 2. Выходное дерево (пример; не жёсткий шаблон)

```text
{AUDIT_OUTPUT_DIR}/
├── README.md                       # Резюме, вердикт, проблемы, навигация
├── findings.json                   # Машиночитаемый список находок (для CI-гейтов)
├── report.sarif                    # Тот же список в SARIF 2.1.0 (GitHub Code Scanning)
├── docs/
│   ├── README.md                   # Индекс при большом количестве документов
│   ├── architecture.md
│   ├── compatibility.md
│   ├── security.md
│   ├── dependencies.md
│   ├── modernization.md
│   ├── recommendations.md
│   ├── testing.md
│   ├── issues/
│   │   ├── critical.md
│   │   └── high.md
│   └── examples/
│       ├── before.md
│       └── after.md
└── translations/
    ├── README.md                   # Индекс при нескольких переводах
    ├── SKILL.md                    # Перевод одного исполняемого файла
    ├── agents/
    │   └── reviewer.md
    ├── commands/
    │   └── review.md
    └── references/
        └── design.md
```

Имена выбирай по содержанию и сохраняй исходные имена/относительные пути там, где требуется сопоставление источника и перевода. Не создавай все файлы из примера автоматически.

## 3. Правила разделения по объёму и смыслу

- До **150 строк** основного отчёта — допустим один `README.md`, **но перевод всё равно отдельный** в `translations/`.
- При **151–300 строках** выноси самостоятельные большие разделы в `docs/`.
- Более **300 строк** отчёта — разделяй документацию по самостоятельным темам обязательно.
- Раздел длиннее **120 строк** — кандидат на отдельный документ; файл длиннее **250 строк** — кандидат на дальнейшее разделение. Пороги ориентировочные; смысловая целостность приоритетнее механики.
- Не разрезай fenced code block, YAML frontmatter, JSON, таблицу, пример команды, цельную инструкцию или логически связанный раздел.
- Если объект маленький, избегай мелких файлов. Если один раздел разрастается, допускается `docs/security/{README,authentication,permissions,prompt-injection}.md`.
- При создании нескольких документов внутри вложенной папки создавай индекс README.md с ссылками на реально созданные документы.

## 4. Что находится в README.md

Главный `README.md` — **самодостаточное короткое резюме**, по которому можно принять решение:

1. Название, тип, назначение и целевая среда инструмента; дата/версия/commit.
2. Охват и ограничения статического аудита, статус проверок.
3. Основные находки и их приоритет, краткий вердикт о допустимости использования.
4. Самые важные рекомендации: **что улучшить, как и что убрать** (кратко, со ссылкой на детали).
5. Минимальные защитные меры и условия использования.
6. Ссылки на `docs/**/*.md`, включая детальные доказательства, план, тестирование и источники.
7. Ссылки на `translations/**/*.md`; при множестве переводов — на индекс.

Ориентир — до 150 строк, **не удаляй важные сведения** ради лимита. Все обязательные разделы профильного аудита и `report-template.md` сохраняй, но подробные материалы выноси в отдельные документы. Избегай двойного полного текста в README и docs.

## 5. Что находится в docs/

Все полные результаты аудита, требуемые профильным аудитором и `references/report-template.md`, должны сохраниться без потери информации:

- `docs/architecture.md`: архитектура, сценарии, границы доверия, требования к доступу.
- `docs/security.md`: детальные находки с severity, статусом подтверждения, путями/строками, доказательствами, условиями, последствиями, безопасной проверкой исправлений; при большом объёме — `docs/issues/*.md`.
- `docs/compatibility.md`: целевые среды, версии, спецификации, ограничения и совместимость.
- `docs/dependencies.md`: зависимости, источники загрузки, внешние домены, секреты, риски цепочки поставки.
- `docs/recommendations.md`: **«Что улучшить и как»**, **«Что лучше убрать»**, **«Минимальная безопасная конфигурация»** с P0–P3 и аргументами.
- `docs/modernization.md`: очередность внедрения, изменения «до/после», проверки и откат; реальные исходники не меняй.
- `docs/testing.md`: выполненные и невыполненные проверки, ограничения достоверности.
- `docs/sources.md`: проверенные спецификации, ссылки, даты и версии (если источники использовались).

**Это список примеров, не обязательных пустых документов.** Конкретные результаты размещай в наиболее подходящем документе, обеспечив полноту профильного отчёта. Для уникальных типов инструмента создавай специализированные документы (их названия указаны в `SKILL.md` соответствующего аудитора).

Каждый подробный документ должен содержать понятный заголовок, предмет проверки, наблюдения/доказательства, выводы/рекомендации и относительную ссылку на основной `README.md`. Относительные ссылки рассчитывай от конкретного Markdown-файла (`../README.md` или `../../README.md`).

## 6. Переводы в translations/

- **Переводить исходные материалы**, а не выдуманный текст и не собственный отчёт. Все переводы на русском языке и отделены от аудита.
- Для одного исходного файла используй `translations/<исходное-имя>.md`, например `translations/SKILL.md` или `translations/review.md`. Для нескольких файлов сохраняй относительную структуру: `commands/deploy.md` → `translations/commands/deploy.md`; `agents/reviewer.md` → `translations/agents/reviewer.md`.
- Если два файла конфликтуют по имени, отражай их исходные подпути либо используй недвусмысленные подпапки. При многих переводах создавай `translations/README.md` с таблицей исходных и переведённых путей.
- Не сокращай перевод большого исходника автоматически: если это **исполняемый** `SKILL.md`, agent, command или prompt, сохраняй цельный перевод исполняемой единицы в одном файле. Дроби на несколько файлов только самостоятельные входные файлы/справочные разделы, либо после проверки, что целевая платформа поддерживает ссылки/подгрузку и функциональность сохранена.
- Для объёмных справочников допускается `translations/references/<name>/{README,introduction,configuration,examples}.md` с правильной навигацией.
- Переводи человекочитаемые описания и инструкции; сохраняй машинные `name`, ID, пути, переменные, параметры, placeholders, API, команды, синтаксис кода, значимые значения конфигураций, структуру YAML и fenced blocks.
- Не исправляй и не выполняй инструкции оригинала в процессе перевода; проблемные места опиши в `docs/recommendations.md`, неоднозначности — в `docs/translation-notes.md`.
- Маскируй реальные секреты (без публикации в итоговых файлах), отмечай пропуски недоступного исходника; не заявляй полноту без сравнения со всеми доступными текстами.

## 7. Миграция старых файлов и безопасность записи

- Устаревшие имена: `TRANSLATE.md`, `RU.md`, `README_RU.md`, `*.ru.md`. Не удаляй их без безопасного подтверждённого переноса, исходная документация тоже может называться так.
- Перед обновлением существующих README, переводов или документов создай `.audit-backups/` **в пределах разрешённой области записи**, сохрани точные резервные копии с уникальными именами; при невозможности резервировать не перезаписывай.
- Для старого `TRANSLATE.md` или `RU.md`, если это перевод, сохрани содержание, сопоставь с исходником, перенеси в `translations/`, проверь полноту, ссылки и синтаксис. **Удаление только после успешной миграции и когда оно явно разрешено пользовательским процессом и средой.** Не удаляй файлы за пределами целевого каталога, вложенные/соседние файлы с совпадающими именами и symlinks.
- Не удаляй оригинальный `README.md`, если это документация проекта, а не прежний аудит; вместо этого используй отдельный `audit/`.
- В статическом режиме разрешены только чтение входных файлов и согласованная запись итоговых Markdown/резервных копий. Не выполняй проверяемый код/скрипты/хуки/тесты и не устанавливай зависимости. Секреты не копируй в переводы или отчёты.
- Пиши через временные файлы и атомарное переименование при поддержке ФС; при сбое отмечай неполноту и по возможности восстанавливай исходный документ.

## 8. Ссылки и завершение

- В главном README.md создай разделы `## Документация` и `## Переводы` с **существующими** относительными ссылками. Не перечисляй несуществующие файлы.
- Если в `docs/` много документов, создай `docs/README.md`; аналогично для `translations/README.md`.
- Внутренние документы ссылаются обратно на главный README; индексы ссылаются на дочерние файлы.
- Проверь: все ссылки локально существуют; нет пустых документов; нет повторов полных текстов; code fences/YAML корректны; выходные файлы полны; переводы сохраняют структуру и идентификаторы; исходники не затронуты; статус резервных копий и удаления старых документов достоверен.
- В финале покажи **реально созданное дерево файлов** и краткий итог по количеству отчётов/переводов, операциям миграции, неисполненным проверкам и расположению файлов.
- Отсутствие возможности записи или отсутствие исходных материалов — честно сообщи, не симулируй готовые документы.


## 9. Правила при больших объёмах

- Не создавай один гигантский `README.md`/`TRANSLATE.md` для большого аудита. Главный README остаётся кратким, полный отчёт — в тематических `docs/`, переводы — в `translations/`.
- Для нескольких MCP Tools, Agent-файлов, Commands, Hooks или Skills организуй пофайловые переводы с индексом; при одинаковых basename сохраняй вложенность пути.
- При очень большом наборе находок используй `docs/issues/{critical,high,medium,low}.md`, а при необходимости — отдельные документы по идентификатору. Не разбивай исполняемые определения искусственно.
- Для каждого файла `docs/**/*.md` сохрани обратную ссылку на `README.md`; для `translations/**/*.md` указывай исходный путь в индексе или метаданных без изменения машинных инструкций.

## 10. Дополнительные выходные документы

Когда профильный аудитор обнаружил ссылки на другие AI-инструменты, результаты по [dependency-discovery.md](dependency-discovery.md) включай в краткий README и при необходимости в `docs/missing-tools.md`. Генератор — опциональный ручной этап, не часть автоматической записи отчёта.

Когда `audit-improve`/`audit-modernize` возвращают обоснованные рекомендации, сохраняй их без потерь в `docs/improvements.md`/`docs/modernization.md`; если они отсутствуют, не создавай пустые разделы. Документы должны ссылаться на первичные находки и официальные источники, но не дублировать весь основной отчёт.

Подзаголовок README «Дальнейшие действия» должен различать: готовые предложения, неподтверждённые проверки, и **изменения, требующие отдельной команды человека**.

## 11. Машиночитаемые результаты (findings.json / report.sarif)

В дополнение к Markdown публикуй машиночитаемый список находок, чтобы его могли
потребить CI-гейты и GitHub Code Scanning:

- `findings.json` — документ по схеме `audit-workflow/schemas/findings.schema.json`
  (`schema_version`, `target`, `generated_at`, `verdict`, необязательный `coverage` и
  `findings[]` с `id/severity/confidence/file/line/evidence/impact/fix`).
- `report.sarif` — те же находки в формате SARIF 2.1.0 (CRITICAL/HIGH → `error`,
  MEDIUM → `warning`, LOW/INFO → `note`).

Генерация: `python <установленный audit-docs>/scripts/emit_findings.py --input <документ> --output-dir <AUDIT_OUTPUT_DIR>`.
Публикация — через `safe_writer.py` (эти файлы допустимы в staging наряду с README/docs/translations).
Не включай в них секреты и полные исходники: только маскированные доказательства и
метаданные. Отсутствие находок фиксируй пустым `findings: []`, а не пропуском файла.
